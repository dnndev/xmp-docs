## Project Overview

This is the **XModPro v5.0+ documentation site**, built with VitePress. It was converted from the v4.x VuePress documentation site and is being updated for v5.0, which is still in active development. It serves a dual purpose:

1. **Public documentation website** — static HTML generated by VitePress
2. **In-app help system** — a `help-content.json` file consumed by the XModPro Vue admin UI

Both outputs are generated from the same set of markdown source files. The in-app help JSON is built by a custom Node.js script that extracts frontmatter and key content sections (Syntax, Example, Attributes) from each markdown file.

Content may still contain v4.x terminology or references that need updating for v5.0. A primary goal of this project is converting the documentation content from v4.x to accurately reflect v5.0 changes.

## v5.0 Terminology Changes

### "Template" → "View"

In v4.x, XMP used "template" to refer to data views (lists, details, etc.). In v5.0, the UI now uses **"View"** to reduce confusion, because the actual XML tags are still called `<xmod:Template>`, `<ItemTemplate>`, `<DetailTemplate>`, etc.

- **"View"** — refers to the data display concept (what the user creates and manages in the UI)
- **"Template"** — refers to the XML tags themselves (`<xmod:Template>`, `<ItemTemplate>`, `<DetailTemplate>`, etc.)

When converting docs, many instances of "template" should become "view", but **not all**. When the text is referring to the actual tag names or tag structure, "template" is still correct. **When unsure, always ask the user.**

## Tone & Audience

Write in a friendly, approachable tone. Do not assume the reader is a developer — many XMP users are site administrators and power users with HTML knowledge, not programmers. Conceptual content, guides, and tutorials should be especially accessible. Reference docs can be more technical but should still be clear and include plenty of examples showing the control or tag in use.

## Deprecations

### ASP.NET Style Properties
Properties like `Font-Bold`, `Font-Size`, `BorderColor`, `BackColor`, etc. are deprecated in v5.0. They still work (XMP controls are ultimately based on ASP.NET controls), but modern web apps use CSS classes via the `CssClass` property or inline styles via the `Style` property. Documentation should:
- Mark these properties as deprecated
- Guide users toward `CssClass` and `Style` instead
- Not remove them from the reference (they still function)

### Frontmatter Schema

Every markdown file requires YAML frontmatter. See `HELP_SCHEMA.md` for the full spec. Required fields:

```yaml
---
id: unique-identifier        # URL-friendly, lowercase with hyphens
title: Display Title          # Human-readable
category: Category Name       # Grouping (e.g., "Input Controls", "Validation")
context: form|template|feed|all  # Where this applies
summary: Brief description    # 1-2 sentences for tooltips/search
---
```

Optional: `since`, `keywords`, `related`, `deprecated`, `deprecatedMessage`.

### Content Structure Pattern

Each control/feature doc follows this structure:

```markdown
# `<TagName>`

Brief introduction.

## Syntax
(code block with tag usage)

## Remarks
* **AttributeName**: Description...

## Example
(code block with example)
```

The build script (`scripts/build-help-json.js`) extracts the Syntax, Example, and Attributes sections via regex matching on these headings.

## Key Scripts

- **`scripts/build-help-json.js`** — Reads all markdown files, extracts frontmatter + content sections, outputs `help-content.json` with topic metadata, category index, and full markdown content.
- **`scripts/add-frontmatter.js`** — Auto-generates frontmatter for files that lack it. Supports `--dry-run` and `--force` flags. Assigns category/context based on directory and filename patterns.
- **`scripts/watch-help.js`** — File watcher (chokidar) that auto-rebuilds and deploys help JSON on `.md` file changes.

## Adding New Documentation Topics

1. Create a `.md` file in the appropriate directory (`form-controls/`, `template-controls/`, `tokens/`, or root)
2. Add frontmatter following the schema in `HELP_SCHEMA.md`
3. Follow the Syntax/Remarks/Example content structure
4. Add the page to the sidebar in `.vitepress/config.mts`
5. If it's a root-level file, add it to `CONFIG.rootFiles` in `scripts/build-help-json.js`
6. Run `npm run help:build` to verify it appears in the JSON output
