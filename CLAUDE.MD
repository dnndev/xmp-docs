## Project Overview

This is the **XModPro v5.0+ documentation site**, built with VitePress. It was converted from the v4.x VuePress documentation site and is being updated for v5.0, which is still in active development.

It produces one output: the **public documentation website** — static HTML generated by VitePress and deployed to `https://www.dnndev.com/help/xmodpro/v5/`.

> **The in-app help system is gone.** XMod Pro v5 no longer embeds help content. The admin UI's **?** button opens the online docs instead (version-pinned to `/v5/`). The old `help-content.json` pipeline — `scripts/build-help-json.js`, `scripts/watch-help.js`, `scripts/add-frontmatter.js`, `HELP_SCHEMA.md`, and the `help:*` npm scripts — has been deleted. Do not regenerate it, and do not reintroduce a build step that writes `help-content.json` anywhere.

Content may still contain v4.x terminology or references that need updating for v5.0. A primary goal of this project is converting the documentation content from v4.x to accurately reflect v5.0 changes.

1. **Look in the drop folder** for recent PNG files (sort by date — newest files are the ones to process)

`{context}-{topic}-{description}.{ext}`

Examples:
- `form-textbox-basic-usage.png`
- `template-datalist-pager-example.png`
- `cp-explorer-main-view.png` (control panel screenshots)
- `tutorial-guestbook-step3-form.png`

Same pattern applies to videos/animations (`.mp4`, `.gif`, `.webm`).

## v5.0 Terminology Changes

### "Template" → "View"

In v4.x, XMP used "template" to refer to data views (lists, details, etc.). In v5.0, the UI now uses **"View"** to reduce confusion, because the actual XML tags are still called `<xmod:Template>`, `<ItemTemplate>`, `<DetailTemplate>`, etc.

- **"View"** — refers to the data display concept (what the user creates and manages in the UI)
- **"Template"** — refers to the XML tags themselves (`<xmod:Template>`, `<ItemTemplate>`, `<DetailTemplate>`, etc.)

When converting docs, many instances of "template" should become "view", but **not all**. When the text is referring to the actual tag names or tag structure, "template" is still correct. **When unsure, always ask the user.**

## Tone & Audience

Write in a friendly, approachable tone. Do not assume the reader is a developer — many XMP users are site administrators and power users with HTML knowledge, not programmers. Conceptual content, guides, and tutorials should be especially accessible. Reference docs can be more technical but should still be clear and include plenty of examples showing the control or tag in use.

## Deprecations

### ASP.NET Style Properties
Properties like `Font-Bold`, `Font-Size`, `BorderColor`, `BackColor`, etc. are deprecated in v5.0. They still work (XMP controls are ultimately based on ASP.NET controls), but modern web apps use CSS classes via the `CssClass` property or inline styles via the `Style` property. Documentation should:
- Mark these properties as deprecated
- Guide users toward `CssClass` and `Style` instead
- Not remove them from the reference (they still function)

## Documentation Work Scope

The conversion work falls into three buckets:

### 1. Rewrite — Admin UI / Control Panel
The control panel is completely rewritten in Vue for v5.0 with significant new features. Pages like control-panel, manage-forms, manage-templates, manage-feeds, database-tools, and form-builder need to be rewritten from scratch with new screenshots and workflows.

### 2. Update — Control & Tag Reference
Core runtime functionality (forms, views, feeds, tokens, controls) is largely unchanged. Existing reference docs need:
- **Terminology pass** (template → view where appropriate)
- **Property accuracy audit** — every public-facing property/attribute of each control and tag must be documented, including whether it is required and its default value
- **Child tag audit** — all child tags must be documented with required/optional status
- **Verification against VB.NET source code** (in the main XMP repo at `C:\Users\kford\source\dnndev\xmp`) to ensure nothing is missing or outdated. The docs should also serve as a Claude-readable reference that makes it easier to keep the help content and the admin UI in sync.

### 3. Create — New Feature Documentation
New docs needed for features that didn't exist in v4.x, including Projects, version history, improved database tools, and others.

### Frontmatter Schema

VitePress consumes only `title` (the page title) and, if present, `description`:

```yaml
---
title: Display Title          # Human-readable page title
---
```

Existing files also carry legacy fields — `id`, `category`, `context`, `summary`, `since`, `keywords`, `related`, `deprecated`, `deprecatedMessage` — left over from the removed in-app help system. **They are inert.** Nothing reads them. Leave them alone in existing files (stripping them across ~140 files is churn for no benefit), but don't add them to new pages and don't spend effort keeping them accurate.

### Content Structure Pattern

Each control/feature doc follows this structure:

```markdown
# `<TagName>`

Brief introduction.

## Syntax
(code block with tag usage)

## Remarks
* **AttributeName**: Description...

## Example
(code block with example)
```

Keep this structure for consistency across the reference pages. Nothing parses it programmatically any more — it's a readability convention, not a contract.

## Issue Tracking

All documentation work is tracked on the **XMP v.5 project board** (project #1) using the `dnndev/xmp-docs` repo.

**Creating issues:**
```bash
# Create issue with labels and milestone
gh issue create --title "Title" --label "docs" --label "update" --milestone "docs-phase-1" --body "Description"

# Add to project board (REQUIRED for every new issue)
gh project item-add 1 --owner dnndev --url <issue-url>
```

**Querying issues:**
```bash
gh issue list --label "docs"                          # All doc issues
gh issue list --milestone "docs-phase-1"              # By phase
gh issue list --label "docs" --label "form-controls"  # By area
```

**Labels:**
- **Type**: `rewrite`, `update`, `new-content`, `property-audit`, `needs-media`
- **Area**: `form-controls`, `template-controls`, `tokens`, `guides`, `admin-ui`, `tutorials`
- **All doc issues**: `docs`

**Milestones:**
- `docs-phase-1` — Foundations (getting started, guides, terminology, tone)
- `docs-phase-2` — Reference Audit (control/tag accuracy, property audit, examples)
- `docs-phase-3` — Admin UI (control panel rewrite, new feature docs)
- `docs-phase-4` — Polish (screenshots, videos, cross-linking, final review)

## Adding New Documentation Topics

1. Create a `.md` file in the appropriate directory (`form-controls/`, `template-controls/`, `tokens/`, or root)
2. Add frontmatter with a `title`
3. Follow the Syntax/Remarks/Example content structure
4. Add the page to the sidebar in `.vitepress/config.mts` — a page not in the sidebar is reachable by URL but invisible in navigation
5. Run `npm run docs:build` to verify it builds and no links are broken
